# 任务泳道与小时排期
**DeepSeek Harness × Codex 双平台插件开发方案 · 2026 年 11 月 20 日 · 首版设计**

## 一、为什么要做

一个人同时开几个 AI 会话做开发时，每个会话都能交代自己在做什么，却很难回答整个工作区的问题。比如，登录模块还在开发，回归测试要等接口稳定，文档整理却随时能做。用户需要直接看到谁在做哪件事、哪个时段被占用、下一件事该放在哪里。

第一张参考图提供了纸卡墙、状态看板和日历。第二张概念图增加小时刻度，把任务重叠和空档放在同一屏。它的数字是示意数据。我们要交付的是一套可操作的工作区：人用网页拖动任务，DeepSeek Harness 和 Codex 在各自对话里查询和修改同一份安排。

### 通俗版

上午，用户让 DeepSeek 把“回归测试”记入工作区，原计划 14 点开始、用时 1 小时。下午开发晚了，用户在时间轴把测试移到 15 点。此时打开 Codex 问“测试几点做”，它应能读出 15 点。15 点到来只表示计划时间到了。实际开测时，由人或参与执行的助手明确登记开始，结束后把结果写回原任务。

### 首版交付边界

| 要解决的问题 | 首版交互 |
| --- | --- |
| 当前有哪些事，分别由谁负责 | 按工作区查看五列看板，任务标注执行方；普通待办也能保存 |
| 什么时候做、安排多久 | 当日按小时显示；移动任务调开工时间，编辑时长；未排期任务单列 |
| 两端如何接续 | 两个宿主共用一组本地 MCP 工具，按同一个任务 ID 读写；从对话取得可视看板入口 |
| 怎样知道实际进度 | 明确上报开始、完成、失败及结果；网页显示当前状态和实际时间 |

本期面向同一台电脑、同一系统用户。跨机协作、依赖自动顺延、定时派发和模型耗时预测另行排期。

## 二、共享数据与双端接入

### 专业版

一个 Python 核心管理一份 SQLite 文件。网页通过环回 HTTP 服务调用核心；Codex 和 Harness 分别启动一个 stdio MCP 子进程，子进程直接调用同一个核心。三个入口使用同一数据库位置。关闭浏览器后，两个宿主仍可读写任务。网页重新读取后显示这些变更。

| 对象 | 数据约定 |
| --- | --- |
| 身份与归属 | 稳定任务 ID、工作区标识、标题、说明、执行方。工作区是逻辑分组；同一操作系统账号下的参与者共享数据库 |
| 计划 | 计划开始可留空，预计时长用正整数分钟。传输和存储使用有时区的时间并统一到 UTC，界面按浏览器本地时区展示 |
| 执行 | 状态包含待规划、待办、进行中、已完成、已失败。实际开始和结束取登记事件的时间，结果保存到任务。人工补登时，登记时间可能晚于真实发生时间 |
| 一致性 | 每条任务有版本号。写入带上读到的版本；冲突返回最新读取提示。失败的客户端重新读取，再提交仍需修改的字段 |

### 宿主适配

**DeepSeek Harness** 在带 MCP 客户端的 Web 或 Desktop 配置中注册本地标准输入输出服务。启动命令选择 Python，参数指向本项目的 MCP 入口。对话可以建任务、读排期、改时间、登记结果，返回的本地链接通往网页。后续可另做 Harness 侧栏按钮，仍调用同一核心。[Harness MCP 客户端配置](https://github.com/deepseek-ai/deepseek-harness/tree/master/packages/mcp/mcp-client)

**Codex** 通过 MCP 配置注册同一入口。用户日常在支持该配置的桌面会话或 CLI 中用自然语言操作；面板在浏览器打开。使用隔离配置验收后，再由使用者把经过验证的命令加入日常配置。两端的 Python 路径、数据库位置和网页地址须指向同一台主机。[Codex MCP 指南](https://developers.openai.com/codex/mcp/)

### 运行边界

数据文件默认存放在当前用户目录，支持显式指定。网页只监听环回地址，不需要云账号。工作区名仅作筛选，不承担用户权限隔离。远端 SSH、容器和本机分别拥有自己的文件系统；若以后要跨机共用，先建设带身份验证的服务 API，统一由服务端写库。

## 三、功能规则与开源取舍

### 排期与执行各自回答什么

1. **改时间。** 拖动只更新计划开始；通过时长字段调整结束位置。仍在待办、尚未排期的任务，也能从看板或清单进入编辑。跨午夜的任务按当天与任务区间的交集显示。
2. **报进度。** 待规划或待办收到开始事件后进入“进行中”。完成或失败事件结束本次执行，保存时间和可选结果。网页按钮和 MCP 工具采用同一套校验。常规编辑保留执行记录。
3. **处理冲突。** 若网页和 Codex 同时修改，只有版本匹配的一方成功。另一方得到冲突提示，重读后可以重新调整。重复提交开始或完成事件不能产生第二次状态变更。
4. **解释指标。** 首版可显示各状态数量、未排期数量和计划时长。两个各一小时、同时执行的任务，应分别计算为两小时任务工时、一小时日历跨度。“可用时段”须先定义某个执行者的工作窗口与并发数，待这些条件齐全再展示。

### 借鉴哪些开源组件

| 组件 | 许可与使用方案 |
| --- | --- |
| DeepSeek Harness 及智能便签插件 | 宿主及所查智能便签包均标为 MIT。参考便签转任务和状态列设计。本项目自行实现共享模型与界面；未来复制具体实现时，随分发保留相应版权和许可声明。[宿主](https://github.com/deepseek-ai/deepseek-harness) · [插件许可](https://raw.githubusercontent.com/0x7A7A6572/dsh-forge-studio/main/packages/plugin-notes/LICENSE) |
| SQLite | SQLite 官方将核心置于公有领域；通过 Python 自带的 sqlite3 访问。事务和版本校验足以支撑单机多进程读写。[SQLite 使用声明](https://www.sqlite.org/copyright.html) |
| 时间轴、看板及 MCP 接口 | 首版使用原生浏览器与 Python 标准库实现，减少安装步骤。协议按 MCP 工具发现和调用规范对接。引入兼容性 SDK 或图表库前，记录版本、许可证和新增分发义务。[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) |

### 后续调度

用户若需要“到点让 Agent 自动开工”，新增独立运行记录、明确的工作目录、启动权限和执行器。调度器先以任务 ID 和本次触发时间锁定唯一运行，再向指定宿主派发；用宿主返回的运行 ID 对账。重启后核对未结束的运行，再决定是否重试。真实结束事件驱动状态回写。这部分与人工改排期独立交付。

## 四、验收、工作量与交付

| 验收场景 | 可观察的通过标准 |
| --- | --- |
| 首次运行与重启 | 空库可启动、可建任务。重启服务并重新打开网页，原任务及最新排期仍可读取 |
| 同库跨端接力 | 入口 A 建任务；网页或入口 B 改排期；入口 A 重读得到同一 ID、新时间和新版本。换工作区后列表隔离 |
| 时间轴交互 | 已排任务可拖动到目标小时；修改时长能改变覆盖范围。未排期、跨午夜、浏览器本地日期分别验证 |
| 真实进度与冲突 | 仅改计划不会登记执行；显式开始和结束后出现实际时间及结果。旧版本改写、重复结束均被拒绝 |
| 双宿主 | 分别检查真实客户端的配置、工具发现和调用；将宿主联调结果与协议自动化测试分开记录。界面下单不等于模型已执行 |
| 发布 | 只提交项目源码、测试、接入说明与方案；排除个人数据库、凭据和临时测试数据。推送后比对本地与远端提交 |

### 工作量预估

按一名熟悉 Python、浏览器交互和 MCP 的开发者估算。以下为人日预算，包含编码和联调时间；现有账号、宿主可启动、范围维持单机是前提。

| 工作包 | 预计投入 | 验收产出 |
| --- | --- | --- |
| 核心模型与持久化 | 0.5–1 人日 | 数据校验、并发写入、执行状态转换 |
| 看板与小时排期 | 1–1.5 人日 | 建改任务、拖动、时长、跨日和窄屏验证 |
| 两端接入 | 0.5–1.5 人日 | 同库工具服务、双端配置、实际客户端联调 |
| 回归与发布 | 0.5–1 人日 | 集成用例、复现步骤、版本与提交核验 |

首版常规预算合计 **2.5–5 人日**，并行开发可缩短日历时间。后续如要求宿主原生面板，另估 1–3 人日；带断线恢复、幂等和两种执行器的定时派发另估 3–6 人日。工程估算随宿主版本和身份验证条件调整。交付时在仓库说明中记录实际通过项、验证方式和未验证的界面。
